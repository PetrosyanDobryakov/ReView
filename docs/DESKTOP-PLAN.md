## 1. Как устроено сейчас (факты из кода, 2026-10-17)

### 1.1. Вес доски = Yjs-док с картинками внутри

- Картинки хранятся **base64 dataURL прямо в Y.Doc**: `src/engine/Engine.ts:2197-2198`
  (при вставке даунскейл до 1600px, JPEG 0.85 / PNG; GIF хранится как есть целиком).
  Видео тоже dataURL (`src/core/media.ts`). Лимит одного файла — 8 МБ (`MEDIA_MAX_BYTES`).
- Локальное хранение — IndexedDB, ключ `review-v1-<boardId>` (`src/core/store.ts:90`,
  `src/core/boardShare.ts:85`). Браузер считает это кэшем: чистка = потеря досок.
- Вес виден в списке досок — `src/core/boardSize.ts` (`estimateBoardBytes`, `formatBoardWeight`).
- Экспорт `.review.json` = base64 всего Y-апдейта + метаданные. Лимиты 32 МБ в трех местах:
  `MAX_FILE_BYTES / MAX_UPDATE_BYTES / MAX_BASE64_CHARS` (`src/core/boardShare.ts:21-23`),
  `MAX_WS_MESSAGE = 32MB` в DO (`worker/src/blob.rs:6`),
  `MAX_WS_PAYLOAD = 32MB` в Node-синке (`sync/netUtil.mjs:7`).

Вывод: "вес доски" — это буквально размер одного Yjs-апдейта, и он же гоняется по сети целиком
каждому новому участнику (sync step1/step2) и лежит в DO целиком.

### 1.2. Сеть сейчас: WebSocket к хабу + зародыш P2P

- `src/net/client.ts` (`SyncClient`, ~1250 строк) — y-websocket к `review-sync`:
  уже сильно оптимизирован под спящий DO (solo-gating awareness — одинокий клиент вообще
  не шлет awareness по WS; текстовый keepalive `review-ka` без пробуждения DO; resync только
  при живых пирах; reconnect backoff 60s). Трогать аккуратно — там выстраданная экономия.
- `src/net/p2p.ts` (`P2pClient`, 522 строки) — y-webrtc уже работает: presence, курсоры, черновики,
  ластики — все то же самое через WebRTC. Сигналинг сейчас чужой публичный `wss://signaling.yjs.dev`
  (`src/net/p2pPolicy.ts`). На `*.workers.dev / *.pages.dev` P2P **принудительно выключен**
  (`src/net/config.ts:91-103`) — было спам-подключение к сигналлингу и лаги.
- Выбор sync URL: LAN/loopback → `:1234`, публичный хост → `wss://review-sync...` (`src/net/config.ts`).
- LAN-инвайты уже есть: `GET /lan`, `lanBoardUrl` (`src/net/lan.ts`).
- Сервер Node (`server.mjs` + `sync/`) и Rust `review-sync` (`rust/`) — WS-хаб на `:1234`,
  комнаты `review-<boardId>`, пустые комнаты GC через ~5 минут.

### 1.3. Cloudflare `review-sync` (за что платим и что болит)

- Rust wasm Durable Object `BoardRoom` (`worker/src/room.rs`, 863 строки): SQLite-персист
  чанками по 1.5 МБ (`STORAGE_CHUNK`), tail-flush 150ms, GC пустых комнат 90s, токен на DELETE.
- Каждое пробуждение DO = деньги (duration + storage + egress). Тяжелая доска = большой blob =

  Именно картинки внутри дока делают blob большим и дорогим.
- Observability уже прижато (`head_sampling_rate = 0.1`, `worker/wrangler.toml:42`) — логи не трогаем.

### 1.4. Tauri-заготовка (что уже есть)

## 2. P2P: возможен ли? (ответ: да, и код наполовину готов)

### Что уже есть

y-webrtc зависимость + `P2pClient` с полным presence. Технически P2P-синк досок возможен уже сейчас —
надо только включить и дать свой сигналинг.

### Что мешает использовать чужой публичный сигналинг в проде

1. `signaling.yjs.dev` — чужой бесплатный сервер. Ложимся, если ляжет он; именно его шторм
   и давал лаги, из-за которых P2P выключили на workers.dev.
2. NAT: STUN пробивает ~80-85% домашних NAT. Остальные (строгие корпоративные/сотовые сети,
   double-NAT у провайдеров) требуют TURN — а TURN ретранслирует трафик через себя,
   т.е. это уже "мини-сервер с трафиком" и деньгами.
3. Нет персистентности: разошлись все — доска живет только в локальных копиях.
   Нужен "кто-то кто всегда онлайн" (super-peer / DO как fallback-хранилище).
4. Тяжелый initial sync через WebRTC datachannel (доска 30+ МБ новичку) медленный и хрупкий.
   Лечится тем же лекарством, что и DO: худой Y.Doc (см. раздел 3).

### Вывод по P2P

P2P — не замена хабу, а **первый ярус каскада**. Правильная роль P2P: живые мелочи
(штрихи, курсоры, presence) напрямую между участниками — ноль байт через Cloudflare.
Тяжелое (первый синк большой доски, картинки, офлайн-пиры) — через хаб/хранилище.
Свой signaling — копеечный WS (можно даже отдельный маленький Worker или VPS рядом с TURN).
Свой TURN (coturn на VPS ~5$/мес) нужен только если среди репетиторов/учеников окажутся
непробиваемые NAT — решать по факту замеров, не заранее.

## 2.5. Видение владельца v2 (зафиксировано, 2026-10-17)

1. **Онлайн = P2P.** Хост жмет "включить онлайн" → анонс в Cloudflare (кто и какую доску раздает) →
   кидает ссылку → гость открывает → Cloudflare сводит их → открывается P2P-соединение.
   Уточнение: Cloudflare пересылает не IP, а WebRTC-сигналинг (offer/answer/ICE-кандидаты);
   сам DO уже видит всех участников комнаты, поэтому отдельный signaling-сервер не нужен —
   DO и есть rendezvous. Если P2P не пробился (строгий NAT) — молчаливый fallback на DO-релей.
2. **Кросс desktop ↔ сайт обязателен** в обе стороны: десктоп раздает → заходят с сайта;
   доска на сайте → заходят с десктопа. Условия: одинаковый формат Y.Doc, одинаковая схема
   хешей блобов, общее blob-хранилище (R2) как мост. Нюанс: https-сайт не может тянуть файлы
   напрямую с http-хоста в LAN (mixed content запрещен браузером) — в связке "сайт + десктоп
   в одной LAN" картинки идут через P2P-datachannel, а не прямым скачиванием.
3. **Блобы по хешу** — подтверждено владельцем, ядро плана (раздел 3).
4. **Загрузка по вьюпорту + LOD.** Новичок первым делом получает видимую область и позицию хоста,
   остальное — по мере скролла. Далекие объекты при отдалении — дешевные превью, полная версия
   докачивается при приближении. Реализация: два разрешения на картинку (превью ~256px + полная
   1600px); чанкинг самого Y.Doc не нужен — после выноса картинок док худой и грузится целиком
   за миллисекунды (вектор копеечный, рендер и так отсекает невидимое).

## 3. Целевая архитектура (как получить идеал + минимум Cloudflare)

### Идея-ядро (одна, самая важная)

**Вынуть картинки из Y.Doc.** Хранить медиа как блобы по content-hash (sha256),
а в Y.Doc — только `{ hash, w, h, mime }`. Тогда:

- Y.Doc худеет с десятков МБ до **десятков КБ** (только векторные штрихи/фигуры/текст);
- синк через DO становится копеечным при любом числе участников (маленький blob =
  быстрое пробуждение, мизер storage/egress);
- лимит 32 МБ на WS фактически перестает достигаться;
- картинки грузятся лениво и кэшируются, а не гоняются при каждом входе.

Хранилище блобов на выбор (решим замеры/бюджетом): Cloudflare R2 (egress бесплатный —
идеально для картинок) или тот же DO чанками (уже умеет, `storage_blob.rs`) или LAN-HTTP
с хоста. R2 — фаворит: платить за хранение копейки, за раздачу — ноль.

### Каскад транспортов (порядок попыток)

1. **LAN WS** (`:1234` / встроенный хост в десктопе): 0 байт через Cloudflare. Урок в одном
   классе/кабинете вообще не выходит в интернет.
2. **P2P WebRTC** (свой signaling): живые апдейты напрямую, 0 байт через Cloudflare.
   Хранилище блобов при этом может быть R2/LAN.
3. **Cloudflare DO**: fallback + rendezvous + персистентность худого дока. Платим только
   за то, что реально нельзя было доставить напрямую.

Плюс десктоп всегда пишет локально в файлы первым делом (offline-first бесплатно —
CRDT это умеет из коробки): нет сети — работаем, появилась — догоняем.

### Файловое хранение в десктопе

Каталог приложения (`%AppData%/ReView` / `~/.local/share` / `~/Library/Application Support`):
`boards/<id>/doc.yjs` (инкрементальные апдейты) + `blobs/<sha256>` + `meta.json`.
IndexedDB остается скоростным кэшем для рендера. Лимит 32 МБ для локальных досок снимаем —
потолок = диск. `.review.json` остается мостом совместимости с сайтом (с предупреждением,
что тяжелую доску сайт может не переварить — честно показать вес при экспорте).

### Дистрибуция

Tauri bundler: NSIS (Win), DMG (Mac), AppImage/deb (Linux) + Tauri updater с диалогом
"доступно обновление". Подпись: Mac — нужен Apple Developer ($99/год, иначе Gatekeeper
будет пугать); Windows — Authenticode-сертификат желателен (без него SmartScreen ворчит,
но ставится). Канал обновлений: GitHub Releases (проще всего) или свой статический URL.

### Этап 2 — блобы по хешу (главный рычаг). Детальная спека

#### 2.0. Исходная точка (что есть сейчас)

- Шейп `image`/`video` хранит байты в поле `src` как dataURL; шейп `doc` — до 60 dataURL страниц
  в поле `pages` (`src/core/shapes.ts:77-78`, `src/core/docImport.ts`, `DOC_MAX_PAGES = 60`).
- Кэш движка `getImage/getVideo` уже принимает `blob:` object URL (`shapes.ts:2908,2938`) —
  рендер почти не трогаем: резолвим `blob-ссылку → blob:URL` и отдаем в существующий кэш.
- Док: Y.Map `shapes` (id → Y.Map полей) + `meta` + `order` + `pages`; compact пересоздает док
  покопийно (`src/core/store.ts:1070-1099`) — миграция едет тем же приемом.
- Есть `isAwarenessLeader()` (`src/net/client.ts`) — миграцию делает только лидер.

#### 2.1. Формат: что лежит в Y.Doc

- Blob = immutable байты, id = **sha256 hex финальных байтов** (после сжатия, не оригинала).
  Одинаковые байты → один хеш → хранятся один раз (дедуп бесплатен).
- Два разрешения на единицу медиа:
  - `full`: правила сжатия как сейчас (1600px / JPEG 0.85 / PNG; GIF — оригинал ради анимации;
    video — оригинал; doc-страницы — JPEG 0.82 / PNG).
  - `thumb`: превью 256px по длинной стороне, JPEG q0.7 (цель ≤100 КБ). GIF — первый кадр
    статикой; video — постер первым кадром через seek+canvas, не вышло — без thumb (иконка в UI).
- Новые поля шейпа (старое `src` deprecated, `pages` у doc-шейпов deprecated):
  `blob: "<sha256>"`, `thumb: "<sha256>" | null`, `mime`, `bytes` (размер full, для прогресса).
  `w/h`, `crop*`, `page` — без изменений. Doc-шейп: `pages: string[]` → `pageBlobs: string[]` +
  `pageThumbs: string[]`.
- Версия формата в доке: `meta.set('blobV', 1)`. Чтение понимает оба варианта
  (`blob` → новый путь; только `src` → legacy-рендер + фоновая миграция). Запись — только новый.
- [ ] Описать тип `BlobRef` в `shapes.ts`, чтение-обертку `resolveMediaSrc(shape)` (blob-ссылка → `blob:` URL).

#### 2.2. Где считается хеш

- Сайт: `crypto.subtle.digest('SHA-256', bytes)` (secure context есть везде: https + localhost).
- Десктоп: Rust-команда `hash_bytes` (стриминг, не грузим весь файл в JS-память) — задел
  под большие файлы.
- Проверка при `put`: пересчитать хеш и сравнить с ключом (защита от битых записей).
- [ ] Реализовать `hashBytes()` (web) + Tauri-команду (desktop) с одинаковым результатом на одних байтах.

#### 2.3. Blobstore: единый интерфейс, пять бэкендов

```ts
put(hash, bytes, mime): Promise<void>  // идемпотентно + verify хеша
get(hash): Promise<{ bytes, mime } | null>
has(hash): Promise<boolean>
```

- `memory-lru` — рендер-кэш (горячие).
- `idb-blobs` — сайт, отдельная база `review-blobs` (доски в `review-v1-*` не трогаем).
- `fs` — десктоп, `blobs/ab/<hash>` (шардинг по первому байту, чтобы не класть 100k файлов в одну папку).
- `lan-http` — `GET /blob/<hash>` с хоста (CORS `*`, immutable-кэш).
- `https` — R2 (фаворит: egress бесплатный) или DO-чанки (`worker/src/storage_blob.rs` уже умеет);
  `Cache-Control: public, immutable, max-age=31536000` везде — блобы immutable по построению.
- `pushMissing(boardId, backend)`: перед шарингом/хостингом сверяем ссылки дока через `has`
  и доливаем недостающее. Десктоп-хост для сайта — пуш в R2; для LAN — достаточно локальных файлов.
- [ ] Интерфейс + `memory`/`idb` бэкенды; [ ] `fs` бэкенд + Tauri-команды; [ ] `lan-http` + `https` бэкенды.

#### 2.4. Загрузка: вьюпорт и LOD

- Рендер: плейсхолдер → очередь → `blob:` URL → существующий кэш движка.
- Приоритет очереди: 1) thumb видимых, 2) full видимых, 3) соседние страницы, 4) остальное.
  Скролл/зум пересчитывает приоритеты, устаревшие fetch отменяются (`AbortController`).
- LOD-правило: на экране < 400px — хватает thumb; больше — full. Thumb держим под full
  до `onload`, чтобы не мигало.
- Хост публикует видимый rect в awareness (тот же hot-batch, что курсор, — почти бесплатно);
  новичок первым тянет то, что видит хост (твое "чанки хоста первыми").
- [ ] Очередь с приоритетами + LOD-правило; [ ] публикация viewport в awareness; [ ] "тяни как у хоста" для новичка.

#### 2.5. Миграция старых досок (двухфазная, без рассинхрона)

- Триггеры: открытие доски новым клиентом (фон, без блокировки UI), compact, import v1.
- Фаза A (переходная): рядом с `src` пишется `blob`; старые клиенты видят `src` как раньше.
  Новые доски — сразу без `src`.
- Фаза B (после обновления всех клиентов: сайт + десктоп): compact дропает `src`/`pages`-dataURL.
- Мигрирует только awareness-лидер; все замены — одна Y-транзакция; в конце `meta.set('blobV', 1)`.
- Серверная миграция не нужна: первый новый клиент мигрирует и персистит худой док
  существующим механизмом.
- [ ] `migrateBoardToBlobs(doc)` + лидер-гейт + хуки в open/compact/import.

#### 2.6. `.review` v2

- Конверт: `{ v: 2, kind, boardId, name, teamId, createdAt, exportedAt, appVersion, pages,
  docUpdate: base64(худой док), blobs: { "<hash>": base64 } }`.
- Import принимает v1 и v2; v1 мигрирует на входе (dataURL → блобы).
- Честный потолок: файл — для досок до ~100 МБ; больше — только P2P/копия папки доски
  (base64 жрет +33% и память).
- [ ] Экспорт/импорт v2 + прием v1; [ ] предупреждение о весе при экспорте тяжелой доски.

#### 2.7. GC и удаление

- Десктоп: mark-and-sweep по всем локальным доскам (собрать все `blob/thumb`-ссылки →
  удалить файлы без ссылок); по кнопке + раз в N дней. Удаление доски — sweep ее хешей
  со сверкой против остальных досок.
- Сервер (R2/DO): точный refcount не ведем (дорого) — TTL 90 дней по последнему доступу
  (`b:<hash>:at`, R2 lifecycle). Контент восстановим с клиентов, потеря не фатальна.
- Приватность: хеш = capability URL (256 бит, не перебирается). Для v1 достаточно;
  приватные доски — ключ комнаты на уровне API (существующие токены).
- [ ] sweep в десктопе; [ ] TTL-правила на сервере.

#### 2.8. Новые лимиты (взамен 32 МБ на все)

- Входной файл: 8 МБ как сейчас (поднять до 32 МБ на десктопе — решить на Этапе 1).
- Full-блоб: результат сжатия (обычно ≤2 МБ); video/GIF-оригинал ≤8 МБ (≤32 МБ десктоп).
- WS-лимит 32 МБ не трогаем — блобы идут мимо WS.
- [ ] Замер: вес Y.Doc типовой фотодоски до/после; трафик DO на вход новичка до/после.

#### 2.9. Что НЕ делаем в Этапе 2

- Не меняем sync-протокол (блобы — отдельный канал поверх тех же комнат).
